# Discovered-Universe Navigation and Direct Travel

Version 1 records the bounded navigation contract for the authored
origin-to-first-target route. It answers the product and scale questions needed
by onboarding contract three without implementing a galaxy renderer, arbitrary
destination generation, fuel, encounters, or a generic campaign system.

## Decision summary

- The player selects a **system**. The application derives and validates the
  jump or direct-travel solution; a mutable solution is not generated by menu
  focus.
- Immutable system anchors exist independently of player knowledge. Unknown
  systems are absent from the navigation view rather than shown as redacted
  generated rows.
- The origin and first target use one versioned route recipe. The route is
  intentionally compact enough for an eccentric continuous trip while FTL
  remains the practical five-second path.
- Knowledge, geometric validity, authorization, affordability, availability,
  and immediate selectability are distinct facts.
- Direct travel crosses explicit local-system boundaries and resolves cruise
  analytically from authoritative ticks. It does not run billions of 120 Hz
  physics steps or depend on render cadence.
- The current no-consumable model makes the route affordable. The endurance
  decision in #133 must retain a completion-and-recovery proof if it later adds
  a resource.

## Generated route and coordinate boundary

The seed domain `navigation=12` is permanent. Version 1 derives route ordinal
one from the universe seed, then uses independent direction and distance
substreams. Generating or inspecting the route cannot consume or perturb
system, star, planet, orbit, station, mission, terrain, signal, or discovery
streams.

The origin anchor is `(0, 0, 0)` integer metres. The first target is placed on
one of the six signed cardinal axes at an independently selected integral
distance from 172,800 through 345,600 light-seconds (48 through 96
light-hours), inclusive. One light-second is exactly 299,792,458 metres. The
bounded cardinal recipe makes coordinates and route length exact across GCC
and Clang without claiming to be a later galaxy-placement algorithm.

Universe and system inertial axes are aligned. A system frame is translated by
its universe anchor; it is not rotated or rescaled. The version-1 local-system
boundary is 100,000,000,000 metres from the anchor, outside the generated
planet bands. A selected direct route begins at the departure boundary with the
live outward velocity and ends at the corresponding destination boundary with
the same velocity. The destination system's analytic ephemerides are resolved
at the unchanged authoritative arrival tick before system flight resumes.

The handoff therefore has no menu teleport: departure position, cruise
position, destination boundary, velocity, and tick form one continuous path.
The version-1 executable proof covers only the authored pair. Arbitrary
catalogs, collision-free placement of later systems, and destinationless deep
space remain follow-up scope rather than hidden generated content.

## Knowledge contract

Generated truth is immutable. Navigation knowledge is mutable or derived
career state and never rerolls that truth.

| Level | Navigation meaning |
| --- | --- |
| `CONTACT` | A stable contact exists and may be named, but exact position and route data are withheld. |
| `PROBABLE` | A bounded sector or distance estimate may be presented, but it is not a valid route solution. |
| `RESOLVED` | Exact system anchor and route geometry are available. |
| `VISITED` | Resolved knowledge plus physical arrival history. |

Unknown systems have no row. `CONTACT` and `PROBABLE` rows do not expose exact
coordinates, distance, ETA, star/planet catalogs, or other immutable generated
facts. Confidence never moves backward and observation later extends this
minimal vocabulary through #97.

The onboarding projection is derived rather than written as earned discovery:

| Career state | Visible navigation rows |
| --- | --- |
| Guided contract one or two | Origin `VISITED` only. |
| Guided contract three | Origin `VISITED`; authored target `RESOLVED`. |
| Skipped or Completed | Origin `VISITED`; authored target `RESOLVED`. |
| Physically at the target | Target becomes `VISITED`; the known origin remains selectable for return. |

Skip therefore gains the documented route access but no visit, mission
completion, reward, probe report, objective delta, or synthetic discovery.

## Destination state

Each visible row exposes the following non-overlapping facts:

| Fact | Definition |
| --- | --- |
| `known` | The view received a `CONTACT` or stronger knowledge record. |
| `valid` | Knowledge is at least `RESOLVED` and the versioned route geometry validates. |
| `authorized` | The current onboarding/mission policy permits this route. |
| `affordable` | The active endurance model can complete the attempted leg. It is true under the current zero-resource model. |
| `available` | The row is valid, authorized, affordable, and not the current system. |
| `selectable` | The row is available and the current travel phase accepts a new selection. |

One disabled reason is shown using this precedence:

1. `current-system`;
2. `requires-resolved-position`;
3. `onboarding-locked`;
4. `insufficient-endurance`;
5. `unavailable-during-travel`.

Malformed generated routes and corrupt identities reject the entire projection
before rows are presented; they are not disguised as an ordinary disabled
destination. During guided contract three exactly one outbound destination is
selectable. Other generated systems do not leak into the view.

## Selection, spool, and commitment

The universe view selects the stable destination `SystemId`. Selection does
not alter generated truth, mission progress, craft pose, or authoritative
time. The existing jump owner then derives its solution at commitment.

| State | Selection and cancellation rule |
| --- | --- |
| View/idle | A selectable system may become the pending destination. |
| Spooling | Destination remains pending; cancel returns to the same live source-system craft state retimed to the current tick. |
| Committed | Destination and immutable arrival are bound; selection and cancellation are disabled. |
| Arrived | The destination is current and receives `current-system`; the known origin may be selected for return. |

Assisted and Pilot use the same generated anchor, knowledge, authorization, and
route status. Their existing alignment and arrival consequences operate only
after selection and cannot reveal or change a destination.

## Continuous non-FTL route

Direct cruise retains the existing maximum system-flight speed of 1,000,000
metres per second. The physical cruise distance is anchor distance minus both
100-billion-metre system boundaries. The route may be sampled at `1x`, `16x`,
`256x`, `4096x`, or `65536x` authoritative time.

One application update advances exactly the selected number of universe ticks.
Position is resolved analytically from the immutable departure state and tick;
no large floating-point integration step and no per-skipped-tick physics loop
exists. Advancement clamps to the exact arrival tick and returns to ordinary
system flight. Pause, render cadence, terminal backpressure, discarded host
catch-up time, and offline real-world waiting do not advance it.

Version 1 has no encounters, consumable fuel, offline progression, or automatic
resource change. Coasting costs zero. #133 may introduce an affordability rule,
but must prove the same authored route completable under Assisted or define a
deterministic recovery; it cannot make the present route silently theoretical.

### Seed-42 reference measurement

The executable `--universe-navigation-acceptance --report PATH` proof records:

| Quantity | Value |
| --- | ---: |
| Direction | `-z` |
| Anchor distance | 321,457 light-seconds / 96,370,384,171,306 m |
| Boundary-to-boundary cruise | 96,170,384,171,306 m |
| FTL spool plus transit | 600 ticks / 5 s |
| Direct cruise at 1,000,000 m/s | 11,540,446,101 ticks / about 1,113 days |
| Updates at 65,536x | 176,094 |
| Ideal 120 Hz host time at maximum scale | 1,467.450 s / about 24.5 min |
| Proposed cruise-state JSON | 386 bytes |
| Resource cost | 0 under the current model |

The direct path is therefore intentionally eccentric but executable. FTL is
the practical route, not a menu-only physical exception.

## Presentation wireflow and budgets

Kitty and ANSI consume one semantic snapshot. Contract three uses two rows and
a detail panel:

```text
UNIVERSE NAV
> ORIGIN   CURRENT / VISITED
  TARGET   RESOLVED / FTL READY / DIRECT 321457 ls

ROUTE: VALID  AUTHORIZED  AFFORDABLE
FTL: SELECT -> SPOOL -> COMMIT
DIRECT: HEADING -Z  ETA 1113 d @ 1000 km/s
```

Color, raster font, and map glyphs may reinforce this information but cannot
replace the row focus, knowledge, disabled reason, route mode, distance, ETA,
or command text. The bounded two-row application renderer has a 1.0 ms p95
budget on the `remote` profile. This research PR adds no renderer or terminal
payload, so it reports `application_contract` evidence only. Contract-three
implementation in #140 must measure application framebuffer/render cost and
Kitty/ANSI encoded bytes separately; live terminal/proxy throughput remains a
separate capture result.

## Persistence and failure behavior

Save format 16 remains unchanged because direct cruise is not active gameplay
in this contract PR. A later active-cruise projection must record the navigation
version, source/destination IDs, departure/arrival/current ticks, exact global
position and velocity, and selected time scale. The canonical reference
projection is 386 bytes and the contract caps the added object below 1 KiB.
System anchors regenerate from the saved universe seed and navigation version;
knowledge and visit history remain mutable state rather than generator input.

Loading or advancing rejects unknown system IDs, route-seed or coordinate
mismatches, invalid knowledge enums, illegal onboarding combinations,
non-finite/fractional/out-of-range speeds, invalid time scales, out-of-range
ticks, and arithmetic or tick overflow. Rejection occurs before selection,
state replacement, rendering, or save commit.
